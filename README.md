# migration-safety-review

AI Skill สำหรับตรวจไฟล์ migration ของฐานข้อมูลก่อนที่คนจะรันจริง ทำงานแบบ **อ่านและวิเคราะห์อย่างเดียว** ไม่รันคำสั่งที่แก้ฐานข้อมูลเด็ดขาด

รายงานที่ได้: ตารางความเสี่ยงรายคำสั่ง (HIGH / MEDIUM / LOW / OK), query ตรวจข้อมูลก่อนรัน, เช็กลิสต์ก่อนรัน, แผนถอยกลับ และรายการสิ่งที่ไฟล์บอกไม่ได้

เอกสารเต็ม (ติดตั้ง ตัวอย่าง prompt ผลทดสอบละเอียด): [.claude/skills/migration-safety-review/README.md](.claude/skills/migration-safety-review/README.md)

## ปัญหาที่แก้

Migration ที่ดูเหมือนไฟล์เล็ก ๆ อาจทำให้ข้อมูลหาย, รันไม่ผ่านกลางทางบนข้อมูลจริง, ล็อกตารางใหญ่จนระบบหยุด หรือถอยกลับไม่ได้ แต่คนมักเห็นปัญหาเหล่านี้หลังรันไปแล้ว Skill นี้ให้ AI ไล่ตรวจแบบเป็นขั้นตอนเดียวกันทุกครั้งก่อนรัน และบอกชัดว่าตรวจอะไรยืนยันไม่ได้

## ทำงานยังไง

```
ไฟล์ migration + บริบท (ถ้ามี)
        |
        v
 1. ระบุบริบท        เครื่องมือ migration, ชนิด DB, ลำดับ dependency
 2. แตกทีละ operation  1 คำสั่ง = 1 แถวในตาราง (ตารางใหม่ที่ว่าง = OK)
 3. จัดหมวดความเสี่ยง  อ่าน references/risk-checklist.md ก่อนให้ระดับ
 4. ให้ระดับ          HIGH / MEDIUM / LOW / OK
 5. เขียนมาตรการ      query ตรวจ, เช็กลิสต์, แผนถอยกลับ, แนวทางแบ่งขั้น
 6. บอกสิ่งที่ไม่รู้   ขนาดตาราง, โค้ดที่ยังใช้คอลัมน์, เวอร์ชัน DB
        |
        v
 รายงานตาม template เดียวกันทุกครั้ง
```

### ขั้นที่ 1: ระบุบริบท
ดูว่าใช้เครื่องมืออะไร (Django, Alembic, Flyway, Liquibase, Prisma, Rails, Knex หรือ SQL ล้วน) และ DB ชนิดไหน เพราะพฤติกรรมล็อกต่างกันตาม DB ถ้าผู้ใช้ไม่ได้บอกขนาดตารางหรือวิธี deploy Skill จะ **ระบุเป็นสมมติฐานในรายงาน** ไม่หยุดถาม ยกเว้นคำตอบนั้นเปลี่ยนความเสี่ยงข้อสำคัญจริง ๆ

### ขั้นที่ 2: แตกทีละ operation
ไล่ทุกคำสั่งในไฟล์ ไม่สรุปรวม ๆ ทุก operation ได้หนึ่งแถวในตาราง ทำให้ผู้อ่านเห็นว่าความเสี่ยงอยู่ที่คำสั่งไหน ตารางไหน คอลัมน์ไหน

### ขั้นที่ 3: จัดหมวดความเสี่ยง
เทียบกับ [risk-checklist.md](.claude/skills/migration-safety-review/references/risk-checklist.md) 6 หมวด (operation เดียวเข้าได้หลายหมวด):

| หมวด | ตัวอย่างที่ตรวจ |
|------|------------------|
| DATA LOSS | ลบคอลัมน์/ตาราง, ลดขนาดหรือเปลี่ยนชนิดจนค่าถูกตัด, เพิ่ม ON DELETE CASCADE |
| CONSTRAINT ON EXISTING DATA | เพิ่ม NOT NULL ไม่มี default, เพิ่ม UNIQUE/FK/CHECK บนข้อมูลที่มีอยู่แล้ว |
| LOCK / DOWNTIME | CREATE INDEX ไม่ CONCURRENTLY, SET NOT NULL, เปลี่ยนชนิดคอลัมน์, UPDATE ทุกแถวใน transaction เดียว |
| IRREVERSIBLE | RunPython ไม่มี reverse_code, RunSQL ไม่มี reverse_sql, การลบข้อมูล |
| DEPLOY ORDER | ลบ/เปลี่ยนชื่อคอลัมน์ขณะโค้ดเก่ายังรันอยู่, เพิ่มคอลัมน์ NOT NULL ที่โค้ดเก่าไม่รู้จัก |
| DATA INTEGRITY | default ไม่อยู่ใน choices, ถอด constraint เดิม, รวม schema กับย้ายข้อมูลก้อนใหญ่ในไฟล์เดียว |

checklist มีหมวดที่ 7 "ที่ไม่ต้องตกใจ" เช่น สร้างตารางใหม่ที่ว่าง หรือเปลี่ยน `help_text` ไว้ลด false positive

### ขั้นที่ 4: ให้ระดับ
ระดับของ operation = ระดับสูงสุดของหมวดที่พบ

| ระดับ | ความหมาย |
|-------|----------|
| HIGH | ข้อมูลหาย, รันไม่ผ่านแน่เมื่อมีข้อมูล, หรือถอยกลับไม่ได้ |
| MEDIUM | ขึ้นกับขนาดข้อมูลหรือลำดับ deploy (ถ้าความเสี่ยงขึ้นกับขนาดตารางแต่ไม่ทราบขนาด ให้เป็น MEDIUM และเขียนว่าต้องรู้ขนาดตาราง) |
| LOW | ผลกระทบเล็กหรือเป็นข้อสังเกต |
| OK | ไม่พบความเสี่ยง |

### ขั้นที่ 5: เขียนมาตรการ
- **query ตรวจข้อมูลก่อนรัน** พร้อมผลที่ยอมรับได้ เช่น หาค่าซ้ำก่อนเพิ่ม UNIQUE, นับ NULL ก่อน SET NOT NULL
- **เช็กลิสต์ก่อนรัน** สำรองข้อมูล, ทดสอบบน staging, ลำดับ deploy, ช่วงเวลาและคนเฝ้า
- **แผนถอยกลับ** ถอยได้ไหม ถอยอย่างไร และข้อมูลส่วนไหนถอยแล้วไม่กลับ (ถ้าไม่มีทางถอย ต้องเขียนว่า "ทางเดียวคือกู้จากสำรองข้อมูล")
- **แนวทางแบ่งขั้น** เช่น expand → deploy โค้ด → contract เมื่อควรแยก migration

### ขั้นที่ 6: บอกสิ่งที่ไฟล์บอกไม่ได้
หัวข้อบังคับที่ห้ามตัด ระบุว่าการตรวจจากไฟล์ยืนยันอะไรไม่ได้ เช่น ขนาดและข้อมูลจริงในตาราง โค้ดที่ยังอ่านคอลัมน์ที่จะลบ เวอร์ชัน DB

## กฎที่ Skill ยึด

- อ่านอย่างเดียว ห้ามรัน migrate / makemigrations / upgrade / flyway / prisma migrate หรือคำสั่งที่แก้ DB
- ห้ามสรุปว่า "ปลอดภัย" ลอย ๆ ต้องบอกว่าตรวจกี่ operation และมีอะไรที่ยืนยันไม่ได้
- ทุกข้อที่แจ้งต้องชี้ operation ที่เกิดเรื่อง (ชื่อ operation + ตาราง/คอลัมน์ หรือเลขบรรทัด)
- เรื่อง lock เขียนว่า "โดยทั่วไป" และแนะนำให้ตรวจเอกสารของเวอร์ชันจริง เพราะขึ้นกับชนิดและเวอร์ชัน DB
- ตารางใหม่ที่ว่างไม่แจ้งว่าเสี่ยงสูง (กัน false positive)
- ไม่แก้ไฟล์ migration เอง เสนอวิธีแก้เป็นข้อความหรือตัวอย่างโค้ด
- ถ้าโปรเจกต์ห้ามให้ AI รัน migration (CLAUDE.md / AGENTS.md) ให้เขียนผลเป็นข้อมูลส่งต่อให้ผู้ดูแลที่รันเอง


## ตัวอย่างผลลัพธ์จริง

จาก [evaluation/case4_B.md](evaluation/case4_B.md) (migration ที่ UPDATE ทุกแถวของตาราง 30 ล้านแถวโดยไม่มี reverse_code แล้วสร้าง index ปกติ) ตารางความเสี่ยงที่ Skill ให้ ย่อมาบางส่วน:

| # | Operation | หมวด | ระดับ | ปัญหาหลัก |
|---|-----------|------|-------|-----------|
| 1 | `RunPython(normalize_event_types)` | IRREVERSIBLE, LOCK/DOWNTIME, DATA LOSS | HIGH | ไม่มี reverse_code, ค่าเดิมถูกเขียนทับกู้คืนไม่ได้, UPDATE 30 ล้านแถวใน transaction เดียว |
| 2 | `AddIndex events_occurred_at_idx` | LOCK/DOWNTIME | MEDIUM | CREATE INDEX ปกติบล็อกการเขียนตลอดการสร้าง |

แล้วต่อด้วย query ตรวจข้อมูล เช็กลิสต์ แผนถอยกลับ ("ทางเดียวคือกู้จากสำรองข้อมูล") และรายการสิ่งที่ไฟล์บอกไม่ได้

## สรุปผลทดสอบ

5 เคส เคสละ 1 รอบ ไฟล์เดียวกัน prompt เดียวกัน เทียบ AI ปกติ กับ AI + Skill

| เกณฑ์ | AI ปกติ | AI + Skill |
|-------|---------|------------|
| เจอความเสี่ยงที่ฝังไว้ | 11/11 | 11/11 |
| ระดับความรุนแรงตรงเฉลย | 8/11 | 10/11 |
| แผนถอยกลับครบ | 2/5 | 5/5 |
| บอกสิ่งที่ไฟล์ยืนยันไม่ได้ | 3/5 | 5/5 |
| false positive ที่เคสปลอดภัย | 0 | 0 |

ข้อสรุป: Skill ไม่ได้จับความเสี่ยงได้มากกว่า AI ปกติ ข้อดีคือรายงานมีโครงสร้างสม่ำเสมอ (query ตรวจข้อมูล แผนถอยกลับ และสิ่งที่ยังไม่รู้)

## ข้อจำกัด

- ทดสอบรอบเดียวต่อเคส ให้คะแนนโดยผู้สร้าง Skill ไม่ได้ปิดตา
- ทดสอบเฉพาะ Django และ PostgreSQL และเรียก Skill ด้วยชื่อ (ยังไม่ได้ทดสอบการทริกเกอร์อัตโนมัติ)
- Skill เห็นแค่ไฟล์ ไม่เห็นขนาดและข้อมูลจริงในตาราง หรือโค้ดที่ยังใช้คอลัมน์ที่จะลบ
- ไม่ใช่การรับประกันว่า migration ปลอดภัย
