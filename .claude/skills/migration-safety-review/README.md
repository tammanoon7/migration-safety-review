# migration-safety-review

AI Skill สำหรับตรวจไฟล์ migration ของฐานข้อมูล **ก่อนส่งให้คนรัน** (หมวด Security / Coding สำหรับงาน backend)

## 1. Skill นี้คืออะไร และแก้ปัญหาอะไร

migration ที่พลาดแล้วแก้ยากเป็นปัญหาที่เจอจริงในงาน backend

- ข้อมูลหาย (ลบคอลัมน์/ตารางโดยไม่ย้ายข้อมูล)
- รันไม่ผ่านกลางทางเพราะมีข้อมูลเดิม (เพิ่ม NOT NULL / UNIQUE / FK บนตารางที่มีแถวอยู่แล้ว)
- ตารางล็อกจนระบบช้า (สร้าง index หรือแก้ตารางใหญ่แบบล็อกการเขียน)
- ถอยกลับไม่ได้ (RunPython ไม่มี reverse, ลบข้อมูล)
- deploy โค้ดกับ schema ไม่ตรงกัน (โค้ดเก่ายังอ่านคอลัมน์ที่ถูกลบหรือเปลี่ยนชื่อ)

หลายทีมไม่ให้ AI รัน migration เอง ให้คนรัน Skill นี้จึงทำหน้าที่ **อ่านและวิเคราะห์เท่านั้น** (ห้ามรันคำสั่งที่แก้ DB ทุกชนิด)
แล้วส่งผลเป็นรายงานให้คนที่จะรัน ใช้ได้กับ Django, Alembic, Flyway, Liquibase, Prisma, Rails, Knex และ SQL ล้วน

โครงสร้างไฟล์

    .claude/skills/migration-safety-review/
      SKILL.md                    คำสั่งหลักของ Skill
      README.md                   ไฟล์นี้
      references/risk-checklist.md  เช็กลิสต์ความเสี่ยง 7 หมวด (Skill อ่านทุกครั้งก่อนให้ระดับ)
      examples/test-cases.md      เคสทดสอบ + เฉลย (ห้ามให้ AI ที่ถูกทดสอบเห็น)
    fixtures/                     ไฟล์ migration ตัวอย่าง 5 เคส (อ่านอย่างเดียว ไม่ต้องรัน)
    evaluation/                   ผลดิบของแต่ละรอบทดสอบ + MANUAL_STEPS.md

## 2. Workflow สรุป 6 ขั้น

1. **ระบุบริบท** เครื่องมือ migration, ชนิด DB, ลำดับ dependency ของไฟล์
2. **แตกทีละ operation** ไล่ทุกคำสั่ง หนึ่งแถวต่อ operation (ตารางใหม่ที่ว่างถือว่า OK)
3. **จัดหมวดความเสี่ยง** ตาม `references/risk-checklist.md` (DATA LOSS, CONSTRAINT ON EXISTING DATA, LOCK/DOWNTIME, IRREVERSIBLE, DEPLOY ORDER, DATA INTEGRITY)
4. **ให้ระดับ** HIGH / MEDIUM / LOW / OK (ถ้าความเสี่ยงขึ้นกับขนาดตารางที่ไม่ทราบ ให้เป็น MEDIUM และบอกว่าต้องรู้ขนาด)
5. **เขียนมาตรการ** query ตรวจข้อมูล, เช็กลิสต์ก่อนรัน, แผนถอยกลับ, แนวทางแบ่งขั้น (expand/contract)
6. **บอกสิ่งที่ไฟล์บอกไม่ได้** ขนาดและข้อมูลจริง, โค้ดที่ยังอ่านคอลัมน์, เวอร์ชัน DB

## 3. Input / Output

**Input**
- ไฟล์ migration หนึ่งไฟล์หรือหลายไฟล์ (หรือวางเนื้อหา SQL มาในแชต)
- (ถ้ามี) ชนิดและเวอร์ชัน DB, ขนาดตารางที่เกี่ยวข้อง, วิธี deploy (ปิดระบบ / rolling)
- ถ้าไม่ระบุ Skill จะเขียนสมมติฐานไว้ในผลลัพธ์ ไม่หยุดถาม

**Output** (Markdown ตาม template ใน SKILL.md)

| ส่วน | เนื้อหา |
|------|---------|
| สรุป | ไฟล์, เครื่องมือ/DB ที่สมมติ, ระดับรวม, คำแนะนำ, จำนวน operation ที่ตรวจแยกตามระดับ |
| ตารางความเสี่ยง | operation, หมวด, ระดับ, ปัญหา, วิธีลดความเสี่ยง (ทุกแถวชี้ operation ที่เกิดเรื่อง) |
| ตรวจข้อมูลก่อนรัน | query พร้อมผลที่ยอมรับได้ เช่น หาค่าซ้ำก่อนเพิ่ม UNIQUE |
| เช็กลิสต์ก่อนรัน | สำรองข้อมูล, staging, ลำดับ deploy, ช่วงเวลา/คนเฝ้า |
| แผนถอยกลับ | ถอยได้ไหม อย่างไร และข้อมูลส่วนไหนถอยแล้วไม่กลับ |
| สิ่งที่ไฟล์นี้บอกไม่ได้ | รายการที่ต้องไปตรวจเพิ่ม |

## 4. ติดตั้ง

**เฉพาะโปรเจกต์** คัดลอกโฟลเดอร์ `migration-safety-review/` ไปไว้ที่ `<โปรเจกต์>/.claude/skills/`

    <โปรเจกต์>/.claude/skills/migration-safety-review/SKILL.md

**ทุกโปรเจกต์** คัดลอกไปไว้ที่ `~/.claude/skills/` (Windows คือ `C:\Users\<ชื่อผู้ใช้>\.claude\skills\`)

    ~/.claude/skills/migration-safety-review/SKILL.md

คัดลอกโฟลเดอร์ `references/` ไปด้วยเสมอ เพราะ SKILL.md อ้างถึง `references/risk-checklist.md`
ส่วน `examples/` มีเฉลยสำหรับทดสอบ ไม่จำเป็นต้องติดตั้งใช้งานจริง

**AI บนเว็บ** (ไม่มีระบบ Skill)
1. เปิดแชตใหม่ วางเนื้อหา `SKILL.md` ทั้งไฟล์ แล้วตามด้วยเนื้อหา `references/risk-checklist.md`
2. พิมพ์ว่า "ทำตาม Skill ข้างบน" แล้ววางไฟล์ migration ตามมา (และบอก DB / ขนาดตารางถ้ามี)

## 5. วิธีใช้ พร้อมตัวอย่าง prompt

เรียกด้วยชื่อ Skill หรือพิมพ์ภาษาปกติที่ตรงกับ description (เช่น "ตรวจ migration", "migration นี้ปลอดภัยไหม")

**ตัวอย่าง 1: ระบุ DB และขนาดตาราง**

    /migration-safety-review ตรวจ migrations/0042_add_status.py ตาราง orders ประมาณ 50 ล้านแถว PostgreSQL 15

**ตัวอย่าง 2: หลายไฟล์ พร้อมวิธี deploy**

    /migration-safety-review ตรวจ migrations/0043_drop_legacy.py และ migrations/0044_add_unique.py ก่อนรันพรุ่งนี้ deploy แบบ rolling ไม่มี downtime

**ตัวอย่าง 3: วาง SQL ลงในแชต ไม่ระบุอะไรเพิ่ม**

    review ไฟล์ migration นี้หน่อย
    ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE (email);

กรณีที่ 3 Skill จะเขียนสมมติฐาน (เช่น DB, ขนาดตาราง) ไว้ในผลลัพธ์ แล้วบอกว่าต้องรู้ขนาดตารางก่อนสรุปความเสี่ยงเรื่อง lock

ผลลัพธ์เป็นรายงานเท่านั้น Skill **ไม่แก้ไฟล์ migration และไม่รันคำสั่งใดกับ DB** ให้คนรับรายงานไปรันเอง

## 6. วิธีนำไปใช้ซ้ำกับโปรเจกต์/เครื่องมือ migration อื่น

SKILL.md ไม่มีชื่อไฟล์หรือกฎเฉพาะโปรเจกต์ จึงคัดลอกไปใช้ได้ทันที ส่วนที่ต้องปรับตามทีมให้ทำนอก SKILL.md

- **กฎเฉพาะทีม** (เช่น ห้ามรัน migration ช่วงเวลาไหน, ต้องมี DBA อนุมัติ) เขียนใน `CLAUDE.md` หรือ `AGENTS.md` ของโปรเจกต์ Skill จะอ่านและเขียนผลเป็นข้อมูลส่งต่อ
- **เครื่องมือใหม่** เพิ่มไฟล์ใน `references/` เช่น `references/tool-notes.md` แล้วให้ SKILL.md อ้างถึง ตัวอย่างสิ่งที่ควรบันทึกต่อเครื่องมือ (ข้อเท็จจริงทั้งหมดควรเขียนว่า "โดยทั่วไป" และตรวจกับเอกสารเวอร์ชันจริง)

| เครื่องมือ | operation ที่ต้องดู | ข้อควรตรวจ |
|-----------|---------------------|------------|
| Django | `RemoveField`, `DeleteModel`, `RunPython`, `AddIndex` | `reverse_code`, `AddIndexConcurrently` + `atomic = False` |
| Alembic | `op.drop_column`, `op.alter_column(nullable=False)`, `op.create_index` | ฟังก์ชัน `downgrade()` ว่างหรือไม่, ตัวเลือก index แบบ concurrent |
| Flyway | ไฟล์ `V__*.sql` | ไม่มีไฟล์ undo คู่กันหรือไม่ (ขึ้นกับเวอร์ชัน/รุ่นที่ใช้) |
| Liquibase | `changeSet` | มี `rollback` กำกับหรือไม่ |
| Prisma | `migration.sql` ที่สร้างอัตโนมัติ | โดยทั่วไปไม่มี down, ดู `DROP`/`ALTER ... NOT NULL` ใน SQL |
| Rails | `remove_column`, `add_index`, `change_column_null` | `algorithm: :concurrently` + `disable_ddl_transaction!`, เมธอด `down` |
| Knex | `exports.up` / `exports.down` | `down` ว่างหรือไม่, index แบบ concurrent ต้องรันนอก transaction |
| SQL ล้วน | `ALTER`, `DROP`, `CREATE INDEX` | ไม่มีทางถอยในตัวไฟล์ ต้องเขียนแผนถอยแยก |

- **ปรับเกณฑ์ระดับความเสี่ยง** แก้ได้ที่หัวข้อ "ให้ระดับ" ใน SKILL.md และรายการใน `references/risk-checklist.md`
- **ตรวจว่ายังใช้ได้ดี** รันชุดทดสอบใน `fixtures/` ซ้ำตามวิธีในหัวข้อ 7 แล้วเทียบกับเฉลยใน `examples/test-cases.md`

## 7. ผลทดสอบเปรียบเทียบ: AI ปกติ (A) vs AI + Skill (B)

ตัวเลขทุกตัวในหัวข้อนี้มาจากผลดิบใน `evaluation/` (ไฟล์ `caseN_A.md` และ `caseN_B.md`) ตรวจเทียบเฉลยใน `examples/test-cases.md`
ทุกช่องมีผลดิบแล้ว แต่ case4 ฝั่ง B รันด้วยวิธีต่างจากรอบอื่น (ดู "เหตุการณ์ระหว่างทดสอบ")

### วิธีทดสอบ

- 5 เคส × 2 ฝั่ง = 10 รอบ แต่ละรอบเป็น agent แยกกัน ไม่เห็นผลของรอบอื่น prompt เดียวกัน "ตรวจ migration นี้ให้หน่อย" พร้อมเนื้อไฟล์จาก `fixtures/` (ฝั่ง B ใส่ `/migration-safety-review` นำหน้า)
- ฝั่ง A: ได้เนื้อไฟล์ใน prompt เท่านั้น และรันก่อนที่ SKILL.md จะถูกสร้างในโปรเจกต์ ฝั่ง A จึงไม่มี Skill ให้เห็นในโปรเจกต์
- ฝั่ง B: ได้เนื้อไฟล์ใน prompt และถูกสั่งให้อ่านเฉพาะ `SKILL.md` กับ `references/risk-checklist.md` แล้วทำตามตรง ๆ
- `examples/test-cases.md` (เฉลย) ถูกสร้างหลังทุกรอบรันเสร็จ จึงไม่มี agent ตัวไหนมีโอกาสเห็น
- จำนวน tool call ที่ระบบรายงานตรงกับที่สั่ง: ฝั่ง A เรียก Write 1 ครั้งต่อรอบ (ยกเว้นรอบรันซ้ำของ case3 ที่ไม่ใช้เครื่องมือเลย) ฝั่ง B เรียก 3 ครั้ง (Read 2 ครั้ง + Write 1 ครั้ง) ผมตรวจได้เฉพาะจำนวน ไม่ได้ตรวจว่าเป็นเครื่องมือตัวไหนจริง
- ไม่มีการรันคำสั่งที่เชื่อมต่อหรือแก้ DB ในการสร้างหรือทดสอบ

### ข้อสังเกต (รวมส่วนที่ไม่เข้าข้าง Skill)

- **การจับความเสี่ยงหลักเท่ากัน** ทั้งสองฝั่งเจอครบ 11/11 AI ปกติจับเรื่องชัดเจนอย่าง DROP COLUMN, NOT NULL ไม่มี default, CREATE INDEX และ UNIQUE ได้ครบเหมือนกัน ตรงกับที่คาดไว้ว่าความต่างไม่ได้อยู่ที่การจับเรื่องชัดเจน
- **ความต่างที่เห็นคือโครงสร้างของคำตอบ** ฝั่ง B มี query ตรวจข้อมูล แผนถอยกลับที่ระบุข้อมูลที่ไม่กลับ และหัวข้อสิ่งที่ไฟล์บอกไม่ได้ ครบทุกเคสที่ทดสอบ ส่วนฝั่ง A ขึ้นอยู่กับเคส เช่น case3 ฝั่ง A สั้น (49 บรรทัด) ไม่มีส่วนสิ่งที่ยืนยันไม่ได้ และมีเพียงข้อความว่า "ควรมี down/rollback script" โดยไม่มีแผน
- **case5 (ตัวควบคุม)** ฝั่ง A สรุปว่า "ปลอดภัย รันได้เลย ไม่พบปัญหาที่ต้องแก้ก่อน deploy" และไม่บอกสิ่งที่ยืนยันไม่ได้ ข้อสรุปนี้ถูกต้องในเนื้อหา (ไม่มี false positive ระดับ HIGH/MEDIUM) แต่ถูกนับว่าไม่ผ่านเกณฑ์ "ไม่สรุปปลอดภัยลอย ๆ" ฝั่ง B ตอบ OK ทั้ง 2 operation พร้อมบอกว่าตรวจครบ 2 จาก 2 และยังมีสิ่งที่ยืนยันไม่ได้ ทั้งสองฝั่งไม่มี false positive ระดับ HIGH/MEDIUM
- **ระดับความรุนแรง** ฝั่ง B ใกล้เฉลยกว่าเล็กน้อย (ทั้งหมด 10/11 เทียบ 8/11) แต่ต่างกันสองรายการ และ case4 ฝั่ง B รันต่างสภาพแวดล้อม ไม่ควรตีความเป็นความต่างที่มีนัยสำคัญ
- **สิ่งที่ฝั่ง B ให้เพิ่ม** ที่เห็นได้ในผลดิบ case3: เตือนว่าถ้า psql ไม่ตั้ง `ON_ERROR_STOP` คำสั่ง DROP COLUMN จะรันต่อแม้ข้อ ADD COLUMN ล้ม และมี query ตรวจ view/index ที่พึ่งคอลัมน์ที่จะลบ ฝั่ง A case3 ไม่ได้พูดถึงเรื่อง `ON_ERROR_STOP` ส่วนเรื่อง view/function มีเพียงข้อความให้ไปตรวจ ไม่มี query
- **ฝั่ง A ไม่ได้แย่กว่าเสมอ** case4 ฝั่ง A ละเอียดมาก (162 บรรทัด) มีโค้ดแก้ไขแบบแยกไฟล์ (migration 2 ไฟล์พร้อม batch) ลำดับ rollout และเตือนเรื่อง collation กับ unique constraint ที่ lower แล้วอาจชนกัน ซึ่งฝั่ง B case4 พูดถึงเรื่อง unique/index เป็นข้อให้ค้นโค้ด และไม่พูดถึง collation ฝั่ง B case4 สั้นกว่า (53 บรรทัด) แต่มี query ตรวจข้อมูล 4 ตัวที่ฝั่ง A ไม่มี
- **ฝั่ง B ยาวกว่า** ในส่วนใหญ่ (case3: 89 เทียบ 49 บรรทัด, case5: 45 เทียบ 24 บรรทัด) เพราะต้องตอบครบทุกหัวข้อใน template แม้เคสที่ไม่มีความเสี่ยงอย่าง case5 ยกเว้น case4 ที่ฝั่ง B สั้นกว่า (53 เทียบ 162)

### ข้อจำกัดของการทดสอบนี้

- รันเคสละ 1 รอบต่อฝั่ง (n = 1) ผลของ LLM ไม่เหมือนกันทุกครั้ง ตัวเลขนี้บอกแนวโน้มได้ ไม่ใช่ผลทางสถิติ
- ผู้ให้คะแนนคือ AI ตัวเดียวกับที่เขียน Skill และรู้ว่ารอบไหนเป็นฝั่งไหน (ไม่ได้ให้คะแนนแบบปิดตา) ควรให้คนตรวจทานการให้คะแนนซ้ำ
- agent ทดสอบใช้โมเดลเดียวกับผู้ให้คะแนน
- ชื่อไฟล์ในโจทย์บอกใบ้ปัญหา (เช่น `case1_drop_without_copy.py`) ผลดิบทั้งสองฝั่งของ case1 อ้างถึงชื่อไฟล์นี้ จึงอาจทำให้ case1 ง่ายกว่าความจริง
- รูปแบบความเสี่ยงใน `references/risk-checklist.md` (เช่น FK NOT NULL ด้วย `default=None`, RunPython ไม่มี reverse) ตรงกับรูปแบบใน fixtures โดยการออกแบบ การทดสอบนี้จึงวัดว่า Workflow ที่อิงเช็กลิสต์ไล่ครบหรือไม่ ไม่ได้วัดว่าจับรูปแบบที่ไม่อยู่ในเช็กลิสต์ได้หรือไม่
- ชุดทดสอบเป็น Django และ PostgreSQL เท่านั้น ยังไม่ได้ทดสอบกับ Alembic, Flyway, Liquibase, Prisma, Rails หรือ Knex
- ฝั่ง B ถูกเรียกด้วยการพิมพ์ชื่อ Skill ตรง ๆ ยังไม่ได้ทดสอบว่า description ทำให้ Skill ถูกเรียกเองหรือไม่
- เนื้อไฟล์ถูกใส่ใน prompt แทนการให้ agent อ่านจากดิสก์ เพื่อให้ทั้งสองฝั่งได้ข้อมูลเท่ากัน
- ตัวอย่าง query ใน `references/risk-checklist.md` ใช้ชื่อ `users`, `email`, `phone` ซึ่งบังเอิญซ้ำกับ case3 อาจทำให้ฝั่ง B ได้เปรียบเล็กน้อยในเกณฑ์ query ของ case3 (ฝั่ง A ก็เขียน query หาอีเมลซ้ำเองได้) ผมไม่ได้แก้ checklist หลังทดสอบเพื่อให้ไฟล์ที่ทดสอบตรงกับไฟล์ที่ส่งมอบ ถ้าจะเปลี่ยนเป็นชื่อกลาง ๆ ควรรันทดสอบซ้ำ
- case4 ฝั่ง B รันโดยคนในสภาพแวดล้อมต่างจากรอบอื่น (ระบบ Skill จริง, โมเดลอ่านไฟล์เอง, Effort Medium, ผู้รันย้ายเฉลยออกเอง) จึงเทียบกับรอบอื่นแบบเงื่อนไขเท่ากันไม่ได้ และผมไม่ได้เห็นการรันนั้นเอง รู้แค่คำตอบที่นำมาบันทึก

## 8. ข้อจำกัด

- **ไม่รู้ขนาดและข้อมูลจริงในตาราง** Skill เห็นแค่ไฟล์ migration จึงตัดสินไม่ได้ว่า query ตรวจข้อมูลจะเจอแถวซ้ำหรือ NULL หรือไม่ และตารางใหญ่แค่ไหน ถ้าไม่ระบุขนาดจะให้ MEDIUM ไว้ก่อน
- **ไม่เห็นโค้ดที่ยังอ่านคอลัมน์** ไม่รู้ว่ามีโค้ด รายงาน หรือ ETL ที่ยังใช้คอลัมน์/ตารางที่จะลบหรือเปลี่ยนชื่อหรือไม่ ต้องค้นโค้ดเพิ่มเอง
- **ความรู้เรื่อง lock ขึ้นกับชนิดและเวอร์ชัน DB** ข้อมูลใน `references/risk-checklist.md` เป็นแบบ "โดยทั่วไป" ควรตรวจกับเอกสารของ DB เวอร์ชันที่ใช้จริงทุกครั้ง
- **Skill ไม่ใช่การรับประกันว่า migration ปลอดภัย** เป็นตัวช่วยตรวจก่อนให้คนรัน ยังต้องทดสอบบน staging ที่มีข้อมูลใกล้เคียงจริง สำรองข้อมูล และมีคนเฝ้าตอนรัน
- **ผลทดสอบยังจำกัด** ดูหัวข้อ "ข้อจำกัดของการทดสอบนี้" ใน 7
