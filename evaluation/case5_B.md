## ตรวจข้อมูลก่อนรัน
ไม่มีข้อมูลเดิมที่ต้องตรวจ (ไม่มี UNIQUE / NOT NULL / FK / CHECK บนตารางเดิม) มีเพียงเช็กว่าชื่อไม่ชนกับของที่มีอยู่แล้ว (อ่านอย่างเดียว ปรับ schema ตามจริง):

```sql
-- ผลที่ยอมรับได้ = NULL ทั้งคู่ (ยังไม่มีตารางและ index ชื่อนี้)
SELECT to_regclass('public.audit_log');
SELECT to_regclass('public.idx_audit_log_created_at');
```

ถ้าได้ค่าที่ไม่ใช่ NULL แปลว่า `CREATE TABLE` หรือ `CREATE INDEX` จะล้มด้วย error "already exists" ให้ตรวจว่าเป็นตารางเดิมของใคร ก่อนตัดสินใจต่อ

## เช็กลิสต์ก่อนรัน

- [ ] ทดสอบบน staging (ตารางว่าง ขนาดข้อมูลไม่มีผล แค่ยืนยันว่ารันผ่านและชื่อไม่ชน)
- [ ] ลำดับ deploy โค้ดกับ migration (รัน migration ก่อนหรือพร้อมโค้ดที่เขียนลง `audit_log` ได้ ไม่มีโค้ดเก่าที่จะพังเพราะตารางนี้)
- [ ] ช่วงเวลาที่ล็อกได้ / คนที่เฝ้า (ไม่จำเป็นเป็นพิเศษ เพราะไม่มีการล็อกตารางที่มีข้อมูล)

## แผนถอยกลับ
- ถอยได้ ถ้ายังไม่มีโค้ดเขียนข้อมูลลงตารางนี้:
  ```sql
  DROP INDEX idx_audit_log_created_at;
  DROP TABLE audit_log;
  ```
  (การ DROP TABLE จะลบ index ตามไปด้วย จึงรันเฉพาะบรรทัดหลังก็ได้)
- ถ้าถอยหลังจากที่แอปเขียน audit log ไปแล้ว ข้อมูลที่เขียนลงตารางนี้จะหายและกลับมาไม่ได้ ทางเดียวคือกู้จากสำรองข้อมูล จึงควรตัดสินใจถอยก่อนเปิดให้เขียนลงตาราง
- ไฟล์นี้ไม่มีส่วน down/undo ในตัว ผู้ดูแลต้องรันคำสั่งถอยเองตามข้างบน

## สิ่งที่ไฟล์นี้บอกไม่ได้
- ตรวจครบ 2 จาก 2 operation ในไฟล์ แต่ไฟล์ยืนยันไม่ได้ว่า `audit_log` และ `idx_audit_log_created_at` ยังไม่มีอยู่ใน DB เป้าหมาย (ใช้ query ในหัวข้อตรวจก่อนรันเช็ก)
- เวอร์ชัน PostgreSQL จริงและ schema ที่จะรัน (ไฟล์ระบุแค่ PostgreSQL 15 ในคอมเมนต์ และไม่ได้ระบุ schema) ข้อเท็จจริงเรื่อง lock ข้างบนเป็นการพูดโดยทั่วไป ให้ตรวจเอกสารของเวอร์ชันจริง
- เครื่องมือ migration ที่ใช้รันไฟล์นี้ (Flyway, psql ตรง ฯลฯ) และรันใน transaction หรือไม่ เพราะมีผลต่อการถอยกลับเมื่อล้มกลางทาง
- ข้อมูลคนที่จะใช้ตารางนี้: โค้ดที่เขียน `audit_log` จะส่งค่า `action` ยาวเกิน 50 ตัวอักษรหรือไม่ (VARCHAR(50) NOT NULL จะปฏิเสธ INSERT) และต้องการ `TIMESTAMP` แบบไม่มี time zone ตามที่เขียนจริงหรือไม่ (เป็นเรื่องการออกแบบ ไม่ใช่ความเสี่ยงของการรัน migration)
